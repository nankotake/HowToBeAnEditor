# 技术方案与引擎选型

> 版本：v0.2 · 2026-08-05  
> 结论先行：**H5 完全可行，推荐先用 Web 原生方案（TypeScript + Vite）做 demo**。产品要原生多平台时，优先"Web 内核 + 原生壳"（Tauri 桌面 + Capacitor 移动）保持一套代码；若编辑器性能/体验不够再迁 Godot 4 重写表现层。用 AI 开发的前提下，Web 栈是最优选，理由见 5.5 节。

---

## 1. 为什么 H5 可行（关键洞察）

这个项目 H5 可行的根本原因只有一条：

> **游戏不处理真实视频。**

《剪单人生》的剪辑是"媒体对象的排列 + 参数组合"，而不是真的编解码视频：

- 素材 = 短视频循环 / 静态图 / 音频 / 文字对象 + 元数据
- 时间线 = JSON 状态（clip 列表、轨道、参数、in/out 点）
- 成片 = 按时间线顺序播放素材的"播放列表"
- 导出 = 播放一遍 + 进度条动画 + 生成交付卡片

因此：

- 无转码、无实时渲染管线，浏览器性能完全够用
- 存档 = 序列化 JSON，天然适合 IndexedDB / 云存档
- 编辑器 UI（面板、时间线、拖拽）是 HTML/CSS/Canvas 的强项
- 不需要 WebAssembly 视频库，开发复杂度大幅下降

## 2. 技术栈推荐

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 语言 | TypeScript | 时间线数据模型复杂，类型系统刚需 |
| 构建 | Vite + 打包产物静态托管 | 快、生态成熟、可出 PWA |
| 状态管理 | Zustand | 时间线是高频变更的中央状态，适合单一 store |
| UI 框架 | React 18（或 Preact 减重） | 面板型 UI 的组件化优势明显 |
| 拖拽 | dnd-kit | 素材拖入轨道、轨道内排序、跨轨拖拽 |
| 时间线渲染 | DOM + 虚拟滚动（首选）/ Canvas（Konva）备选 | DOM 便于选中态、hover、上下文菜单 |
| 预览播放 | `<video>` 拼接播放 + canvas 覆盖层 | 异常帧/贴纸用覆盖层叠加渲染 |
| 音频 | Web Audio API / Howler | BGM、音效、倒放音效等 |
| 动画 | GSAP | 转场预览、UI 过渡、导出动画 |
| 存档 | IndexedDB（Dexie 封装）+ JSON 导出 | 项目档案可备份/分享 |
| 发布 | 静态站点 / PWA / Capacitor 套壳 | 一条代码多端 |

> 若目标含微信小游戏：需评估 dnd-kit 与 DOM 拖拽在小游戏环境（无 DOM）的限制，届时可改用 Canvas 渲染时间线或换 Phaser。

## 3. 架构设计

### 3.1 分层

```text
┌──────────────────────────────────────────┐
│ 表现层：React 组件（面板/时间线/预览/HUD） │
├──────────────────────────────────────────┤
│ 逻辑层：编辑器命令（剪/拖/变速/调色...）   │
│         需求判定 · 评分 · 异常触发         │
├──────────────────────────────────────────┤
│ 数据层：Project / Timeline / Order /      │
│         Save / Settings                   │
└──────────────────────────────────────────┘
```

### 3.2 核心数据模型

```ts
interface Project {
  id: string;
  orderId: string;
  name: string;
  timeline: Timeline;
  createdAt: number;
  status: 'draft' | 'delivered' | 'revision';
}

interface Timeline {
  tracks: Track[];          // V1 / V2 / A1 / Subtitle
  duration: number;
  playhead: number;
}

interface Clip {
  id: string;
  sourceId: string;         // 素材 id
  type: 'video' | 'image' | 'audio' | 'text';
  trackId: string;
  in: number;               // 素材内裁剪点
  out: number;
  start: number;            // 时间线上位置
  speed: number;
  reversed: boolean;
  transform: { x: number; y: number; scale: number; rotate: number; opacity: number };
  colorGrade: string;       // 预设 id
  muted: boolean;
  volume: number;
  anomalies: AnomalyRef[];  // 该 clip 暴露的异常引用
}

interface Order {
  id: string;
  client: Client;
  brief: string;            // 需求文案
  hardRequirements: Requirement[];
  softRequirements: Requirement[];
  budget: number;
  deadline: number;
  materials: MaterialRef[]; // 素材包（含隐藏异常）
  hiddenChecks: HiddenCheck[]; // 评分暗线
}
```

### 3.3 命令模式与撤销重做

编辑器体验的根基。所有操作走命令：

```ts
interface EditCommand {
  apply(state: Timeline): Timeline;
  undo(state: Timeline): Timeline;
}
```

- 撤销栈 / 重做栈，Ctrl+Z / Ctrl+Shift+Z
- 存档保存 undo 栈，方便"回到任意历史版本"

### 3.4 异常系统实现

- 异常不存于素材本身，而是**素材元数据层**：`Anomaly { id, type, trigger: {at: number, duration}, render: 'flashFrame' | 'bgFigure' | 'reversedAudio' | ... }`
- 预览播放时，渲染层根据 playhead 叠加异常（闪一帧、角落人影、混入音频）
- 玩家"标记"后写入自己的线索本，不影响时间线数据
- 是否"剪进成片"= 时间线上该异常对应 clip 是否保留/突出，评分与剧情按此判定

## 4. 性能与适配

- 单项目素材上限：30–50 个（超出给"素材太多，建议精简"的演出，而非卡死）
- 时间线虚拟滚动：只渲染可视区 clip
- 缩略图懒加载 + 生成小图缓存（IndexedDB）
- 低端机降级：关闭实时转场预览、降低异常特效、时间线简化渲染
- 移动端：触屏拖拽适配，窄屏切"简化模式"（隐藏素材库，改为底部抽屉）

## 5. 引擎对比（备选方案）

| 方案 | 优点 | 缺点 | AI 开发适配 | 适用场景 |
| --- | --- | --- | --- | --- |
| **Web 原生（推荐）** | 编辑器 UI 天花板最高；存档/分享天然；开发快 | 无现成游戏框架，需自建系统 | ★★★★★ 训练语料最多、模式最标准，AI 幻觉率最低，浏览器实时预览便于自查 | H5 demo 与产品化的首选，核心是 UI 编辑器而非动作玩法 |
| Phaser 3 | 游戏循环/粒子/动画成熟，导出小游戏容易 | 复杂 UI（面板/时间线）实现痛苦 | ★★★☆ 语料多，但"用游戏引擎写 UI"容易生成反模式代码 | 后期大量加动画演出/小游戏关卡时局部引入 |
| Godot 4（Web 导出） | Control 节点做 UI 强，可导出 Web/桌面/移动；免费 | WebGL 包体偏大、加载慢；4.x API 变动频繁 | ★★★★ 官方文档质量高，但语料少于 Web 栈，AI 可能写旧 API 代码，需多纠错 | 若 Web 原生性能/体验失控，迁到"单引擎原生"的首选 |
| Unity | UI 与资源管线最成熟 | WebGL 包体大、上手重、非本类型最优 | ★★★★ C# 语料极多，但工程臃肿，AI 容易把简单事做复杂 | 基本不推荐，除非团队本就熟 C#/Unity 管线 |

### 迁移策略

- 数据层与逻辑层与渲染层解耦（上面的分层架构）
- 若未来迁 Godot：时间线 JSON 模型可直接复用，只需重写表现层
- 现阶段不做引擎绑定，先跑通 Web 原生原型

### 5.5 用 AI 开发时怎么选（直接回答）

AI 生成代码的可靠性取决于三个因素：**训练语料规模、API 稳定性、模式标准化程度**。按此排序：

1. **Web 栈（TS/React/Vite）**：语料最大、模式最标准、错误最容易自查（浏览器实时预览），是用 AI 开发时效率最高、返工最少的选择。
2. **Godot 4**：语料中等但官方文档结构清晰，AI 可胜任；缺点是 4.x 版本 API 变动多，AI 偶尔生成旧版 API 代码，需要留纠错预算。它是"单引擎原生"路线里 AI 最可用的。
3. **Unity/C#**：语料很多，但工程结构重，AI 生成的代码容易"正确但笨重"，对这个 UI 驱动型游戏是杀鸡用牛刀。

AI 开发实操建议：

- 模块保持小而清晰（每个文件只干一件事），AI 生成质量显著更高
- 让 AI 先写数据模型和纯逻辑（时间线、评分、订单判定），再写 UI；UI 复杂时拆组件逐个生成
- 数据层与渲染层解耦（第 3 节架构），换引擎时只重写表现层
- 关键功能配单元测试（时间线操作、撤销重做、评分计算），AI 写测试也很快
- 锁定依赖版本，AI 踩 API 变动坑的概率会大幅下降

## 6. 需要的开发资源

### 6.1 人力

| 角色 | 数量 | 职责 |
| --- | --- | --- |
| 全栈/前端程序 | 1–2 | 编辑器、时间线、状态、存档、游戏逻辑 |
| 游戏/UI 设计师 | 1 | 玩法数值、UI 布局（Resolve 风格）、交互稿 |
| 美术 | 1 | 素材资产、客户立绘、图标、界面皮肤 |
| 文案/编剧 | 1（可兼职） | 需求文本、对话、主线剧本（**内容大头**） |
| 音频 | 外包/兼职 | BGM 曲库、音效、异常音 |

最小可启动团队：**程序 1 + 设计 1 + 文案 1**，美术音频外包。

### 6.2 素材生产策略

- 素材用程序化/生成式管线批量产出：模板 + 随机化（人物动作循环、场景、字体、滤镜）
- 短视频素材可用开源素材（Pexels 等免版权）+ 后期统一调色做风格化
- 异常素材复用件 + 参数随机，避免玩家背版
- 工具建议：剪映/PR 批量出素材、Blender 做 3D 循环、AI 生成文案草稿后人工润色

### 6.3 工具链

- Git + GitHub（版本与协作）
- 项目管理：Linear / 飞书 / Trello
- 原型工具：Figma（UI 稿，直接参考 Resolve 截图做风格稿）
- CI：Vercel / Netlify 自动预览部署（方便试玩）
